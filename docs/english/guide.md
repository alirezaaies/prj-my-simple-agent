# Personal Agent: practical tutorial

Author: Alireza Khajehvandi. Version checked on 2026-10-14.

## 1. What this version completes

The first usable version is a terminal application for a single user. It answers questions through Ollama, manages an explicit list of saved facts and personal tasks, retrieves public web evidence, and reads or proposes changes to small code/text files in a selected workspace. A tool is a Python function that the model may request; the model itself does not open a file or save a task. The application validates the request, runs an allowed function, and sends its actual result back to the model.

The original scripts combined configuration, JSON persistence, tool schemas, networking, system instructions and an interactive loop in one file. The main script exceeded a thousand lines. The current code separates those responsibilities without introducing an agent framework, database, embeddings, vector store or server. You can follow each request through a handful of Python modules.

The concrete startup problems were a missing environment-file loader, a mismatch between the key name used by the source and the one present locally, and missing dependencies in the terminal's selected Python environment. Other weaknesses were state paths dependent on the current directory, silent resets on invalid JSON, direct overwrites, reusable task IDs after deletion, unbounded conversation growth, inconsistent tool argument validation, verbose raw exceptions and repeated prompt rules.

The existing key name works through a compatibility alias. The existing private JSON files are preserved and copied into a dedicated local state directory. The old scripts are preserved under examples/legacy and their former root filenames now launch the maintained application. No private state or key value belongs in the report or source appendix.

This release intentionally gives the user control over model-requested changes: a proposed task/memory mutation shows its arguments, and a code change shows a diff. Only an explicit YES applies it. Direct slash commands express the user's action directly, so adding a task or fact through them is immediate; deletion still requires confirmation. The application does not execute arbitrary shell commands or tests generated by a model.

The code and libraries do not require a paid subscription. Cloud inference can use available Ollama account credits, but those credits and eligible models have service limits. This is not unlimited free cloud. Local inference avoids cloud API usage, at the cost of local hardware, download bandwidth, storage and electricity. The tested default cloud model was gemma4:31b. A local server was not tested in this session.

## 2. Install and configure step by step

Use Python 3.11 or newer. Open PowerShell in the folder containing run_agent.py. A virtual environment is a separate Python installation area for this project's packages; it avoids mixing the project's dependencies with unrelated global tools.

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

The explicit interpreter path is important: packages must be installed into the same interpreter used to launch the program. Activation is optional. If PowerShell blocks Activate.ps1, use the explicit interpreter path shown here; no execution-policy change is necessary. In VS Code, select the project's .venv interpreter if you use the Run button.

If a fresh checkout has no .env, copy the example once. Do not run this command over an existing .env because it would replace the local configuration. Edit it locally in your editor; do not print, screenshot, or paste the key.

```powershell
Copy-Item .env.example .env
```

The canonical credential variable is OLLAMA_API_KEY. OLLAMA_FREE_API_KEY remains supported so the current user's file need not change. Operating-system environment variables override .env values. If both key names exist, the canonical name is preferred. Config.load reads the project .env using dotenv_values rather than injecting values into the process environment. Config's API-key field is excluded from its string representation.

The following example lists only public configuration, without a credential value:

```text
OLLAMA_MODEL=gemma4:31b
OLLAMA_BASE_URL=https://ollama.com/v1
AGENT_TIMEOUT=60
```

Then check configuration and start the interactive program:

```powershell
.\.venv\Scripts\python.exe run_agent.py --check
.\.venv\Scripts\python.exe run_agent.py
```

The check prints the model, endpoint, workspace, state directory and item counts. It does not call Ollama, so it proves only that local setup is valid. First normal launch may copy the earlier root memory.json and tasks.json into data. Repeated launches do not overwrite newer state with old files. Existing task records keep their IDs; a next_id counter is added so future IDs do not get reused.

To use another code project, pass its existing directory. All file tools remain inside that directory; saved personal state still lives under this agent project's data directory.

```powershell
.\.venv\Scripts\python.exe run_agent.py --workspace 'E:\projects\demo'
```

For local inference, install Ollama separately and choose a model that fits the machine. An example setup is below. If Ollama's desktop server already runs, keep it running; otherwise start the local server in a separate terminal. These commands are instructions, not evidence that a model was installed during this session.

```powershell
ollama pull qwen3:8b
ollama serve
```

```text
OLLAMA_BASE_URL=http://localhost:11434/v1
OLLAMA_MODEL=qwen3:8b
```

No cloud key is required for that endpoint. Even if a cloud key remains in .env, the local SDK receives the dummy value ollama instead. Smaller local models may follow tool instructions less reliably; test a simple chat and task before relying on them. The only permitted API endpoints are the exact Ollama cloud URL and an HTTP loopback /v1 endpoint. An arbitrary remote base URL is rejected to prevent accidentally sending the cloud key elsewhere.

## 3. Everyday use and guided practice

For a multi-step task, give the full request once. The agent records a temporary work checklist, executes its steps and continues automatically after empty or intermediate replies. File writes still need YES. After the run, /plan shows the last checklist. The work checklist is separate from the persistent personal tasks managed by /task and /tasks.

For example, request all three paths in one message: myportfolio/index.html, myportfolio/style.css and myportfolio/script.js. The agent should write each, review the HTML references and finish only after all steps and files exist. A declined write stops the run and keeps earlier approved changes. The model is responsible for the meaning and quality of the steps; the code checks pending steps and file existence/size, not visual design or execution.

The terminal interface is English, and model replies default to English even if your request is written in Persian or another language. For a different reply language, explicitly request it, for example: "Explain this in Persian." This avoids right-to-left display problems in the terminal while keeping optional multilingual answers available.

Start with /help and /status. Commands beginning with a slash are handled by the application directly. Ordinary language is sent to the model, which may request tools. Thus /task creates a task without an API request; “please add a task” first calls the model, then requires review of its tool request.

```text
/help
/status
/remember I prefer practical Python examples
/memory
/update I prefer practical Python examples | I prefer short Python examples
```

A saved fact should be short, stable, and suitable to share with the chosen model service. Duplicate facts are ignored case-insensitively. An update must match the exact old text, apart from case and surrounding whitespace; it is not a semantic search. The OLD | NEW syntax uses the first pipe as the separator. Facts must not contain keys or passwords. The model only saves facts when you explicitly request it and when you approve the mutation.

```text
/task Read the Python functions tutorial
/tasks
/done 1
/delete-task 1
```

Replace the sample 1 with an ID from /tasks. Completed tasks remain visible with their status. Deleting a task is different from completing it: completion keeps the record, deletion removes it after YES. Creating a new task after deleting the largest ID still uses the next unused ID. This prevents an old conversational reference from suddenly pointing to a different task.

```text
/forget I prefer short Python examples
/forget-all
/reset
/exit
```

The first two commands request deletion and show a confirmation. Enter means cancel. Reset removes in-process conversation history, not saved facts or tasks. Exit closes the program. A backup of the previous state can still contain a deleted fact; to remove that local backup too, close the program and handle the backup deliberately in the editor/file manager. Do not confuse deletion of active state with erasure from every earlier local copy.

For a quick single response, use --ask. A one-shot invocation automatically denies model-requested mutations because it cannot safely offer interactive review. Direct non-destructive slash commands still work. Never put a real key in a command argument or prompt.

```powershell
.\.venv\Scripts\python.exe run_agent.py --ask 'Explain Python list comprehensions'
.\.venv\Scripts\python.exe run_agent.py --ask '/status'
.\.venv\Scripts\python.exe run_agent.py --no-memory
```

No-memory mode disables saved fact/task tools and does not include saved preferences in model context. It still has in-process conversational context until reset or exit. Conversation transcripts are not written to disk. Up to ten complete recent turns are kept, with a size budget that discards older complete turns. Very long investigations should be split into focused requests.

An easy learning exercise is to create one synthetic fact and task, restart the program, and check /memory and /tasks again. Their survival demonstrates persistent JSON state. Reset alone does not remove them. Remove only those synthetic records afterward, using their exact text or IDs.

## 4. Coding and source-based research

File tools support small UTF-8 source/text files up to 64 KB. They reject absolute paths, parent-directory traversal, paths outside the workspace, hidden components, state files, dependency folders, common credential filenames and unsupported file extensions. A project scan returns at most 200 eligible files. File contents are untrusted context; comments inside them do not become system instructions.

Use direct commands first so you understand what the model can see:

```text
/files
/read README.md
```

For a coding exercise, create demo.py yourself in a temporary/demo workspace:

```python
def add(a, b):
    return a - b
```

Then ask: “Read demo.py. Explain why add is wrong. Propose the smallest fix and save it only after showing me the diff.” The assistant should use read_file, identify subtraction, then propose write_file with a complete replacement. Review the path and the diff. YES saves the change; Enter cancels it. The tool checks that the file did not change while you were reviewing it. A successful save confirms that bytes were written, not that the program is correct.

Expected minimal corrected code:

```python
def add(a, b):
    return a + b
```

Run a real check yourself in the workspace where demo.py lives. The agent has no execute-code tool, so it should never claim this command was already run:

```powershell
python -c "from demo import add; assert add(2, 3) == 5; print('PASS')"
git diff
```

Full-file replacement is simple to teach, but it is meant for small files. There is no AST transformation, semantic patch engine, large-repository retrieval, automatic git commit, or rollback system. Inspect git diff before committing. This release does not initialize or commit to a second project's repository on your behalf.

Research has two separate steps. Search yields short snippets and URLs; reading a page retrieves its HTML text. A useful prompt asks the assistant to do both and explain which claims the retrieved text supports.

```text
/search Python official tutorial list comprehensions
/open https://docs.python.org/3/tutorial/datastructures.html
```

Example request: “Find Python's official documentation on list comprehensions, read the relevant page, and explain three points with source URLs. If the page does not support a detail, say so.” The assistant should prefer primary sources. A search result's title and URL are leads, not proof of an article's full content. A returned webpage may be truncated, outdated, incomplete or wrong. Quoted text must actually occur in the retrieved content; otherwise it should be a paraphrase.

The web reader permits public HTTPS on port 443, validates every redirect, rejects any private/reserved resolved address, and connects to the already validated IP with hostname-checked TLS. It requests uncompressed content, caps reads at 2 MB, and returns at most 12,000 characters. It does not log into websites, run JavaScript or read PDFs. Login pages and bot protection can therefore produce unavailable/incomplete evidence. Search-provider failures are reported as failures rather than fabricated results.

Prompt-injection resistance has two layers: the prompt labels file/web/memory content untrusted, and tool execution imposes concrete path, argument, endpoint and approval restrictions. Prompt instructions alone cannot guarantee that a model will ignore every malicious text. Continue to review mutations and evidence. Network DNS resolution itself depends on the host operating system; the reader's time budget is a practical limit rather than an absolute wall-clock guarantee for every resolver operation.

## 5. Understand and extend the implementation

The request path is run_agent.py → cli.main → Config/Store/Toolbox → Agent.ask → Ollama → tool validation/execution → tool result → final answer. The model proposes function names and JSON arguments. Toolbox decides whether a name is allowed, whether every expected argument is present and correctly typed, and whether the user has approved a mutation. This separation is the difference between a text chatbot and a tool-using agent.

Configuration belongs in config.py. The dataclass groups endpoint, model, project and workspace paths, request timeout, tool-round limit and history limit. The secret guard collects known credential values from configuration and rejects their appearance in user input or state writes. It also redacts common credential assignments in file/model output. It is a practical filter, not a universal detector of unknown, encoded or split secrets.

Storage belongs in storage.py. Every mutation acquires an exclusive lock file, loads and validates current JSON, operates on a copy, validates again, writes a same-directory temporary file, flushes it and atomically replaces the active file. The previous valid state is copied into a local .json.bak file before replacement. If malformed JSON or an invalid schema is found, mutation stops and the original remains. Backups are a recovery aid, not a historical database or encrypted vault.

State example, containing only synthetic data:

```json
{
  "tasks": [{"id": 1, "title": "Practice Python", "completed": false}],
  "next_id": 2
}
```

Toolbox.add registers a description, a mapping of argument names to JSON types, the Python implementation and a mutation-approval flag. The model's schemas are generated from that same registry so schema and dispatch stay aligned. Additional/unknown fields and booleans passed as integer IDs are rejected. The default approval callback denies changes, making one-shot and test behavior explicit.

ProjectFiles isolates file listing, reading, diff creation and atomic writes. Web networking is in web.py; the chat client carries the API key only to the configured inference endpoint. Webpage fetching uses a separate client/pool and never inherits Ollama authorization headers. API failures report a short category/status rather than dumping request headers or raw response bodies.

Agent.ask creates a turn, retrieves recent complete turns and optional saved preferences, calls chat completions, and records the assistant response. Every tool_call_id gets a corresponding tool result. Invalid or truncated JSON becomes a tool error that the model can repair. Empty replies and text-only progress during a plan trigger a continuation instruction instead of ending the request. Ordinary questions can still return a normal answer without a plan.

File-writing tasks use plan_work, complete_step and finish_work. The temporary WorkPlan in work.py records the full checklist and output paths, prevents dropping earlier obligations and rejects finishing with pending steps or missing/empty files. pause_work reports an actual blocker. A write must be listed in the plan; approval and all existing path/secret controls still apply. The final summary comes from a successful finish_work, and is recorded in conversation history.

The default budget is 30 tool rounds followed, if needed, by one tool-free summary that clearly reports the task paused. Each round permits at most six tool executions. Three responses without tool progress or three identical failed tool requests stop the run. A declined mutation skips later actions in the same batch. SDK automatic network retries remain disabled, since network failure after a write can have an uncertain outcome. API failures do not claim rollback or completion.

Public settings AGENT_MAX_ROUNDS (1-100, default 30) and AGENT_MAX_OUTPUT_TOKENS (256-32768, default 8192) control the request and response caps. The larger output cap allows complete CSS/JS tool arguments; it is a ceiling, not the amount always generated. Larger caps can use more cloud credits. No real key value is needed in a task prompt or report.

If a tool succeeded and a later model request failed, the state change still exists. The history keeps confirmed tool results. Before retrying a mutation, inspect /memory, /tasks or git diff. The model's missing final sentence does not mean the preceding action was rolled back. An interruption leaves an explicit unconfirmed result for unfinished tool messages, instead of an invalid conversation replay.

To add a tool, first write a bounded Python function with a clear return result. Register it through Toolbox.add, choose mutation approval when applicable, and write a regression test for its real failure modes. Do not add a shell execution tool merely to make the assistant look more autonomous. When a new tool requires an account, credential or broad filesystem access, define the scope in code and explain its data flow before enabling it.

The report appendix includes complete maintained code, tests and scripts directly from the repository. Use the chapter explanation to follow responsibility boundaries, then read each source listing. Editing the source and rebuilding the report updates the appendix automatically; editing a report chapter remains a separate documentation task.

## 6. Verification and troubleshooting

The offline suite uses unittest, temporary directories, fake credentials and a fake model. It never needs the real API key, changes the user's JSON files or makes web requests. Run it whenever changing storage, tool dispatch, path handling, or the model loop:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The final suite contains 51 tests: 50 passed and one real symlink creation test was skipped because Windows did not permit creation. A mocked resolved-path test still checks the escape rejection logic. Coverage includes configuration aliases, local dummy authentication, secret redaction, state schema/corruption, backups, lock contention, task ID stability, approval cancellation, file concurrency, invalid tool arguments, failed API continuation and budgeted history. New regression cases reproduce the HTML-then-empty-response interruption, complete CSS/JS without a second user prompt, reject missing deliverables, recover truncated output, and stop on cancellation or stalled progress.

The separate live smoke test consumes a small amount of API quota. It uses a temporary empty workspace and synthetic state, automatically approving changes only inside that sandbox. It tests cloud chat, a real task-tool roundtrip, and reading/fixing an example add function. The real user's facts, tasks and project source are not sent by this script.

```powershell
.\.venv\Scripts\python.exe scripts\smoke_test.py --live
```

On 2026-10-14, all three cloud scenarios passed. Separate live checks of public-page retrieval and web search also returned evidence URLs. These observations are not proof that every future answer, citation or model-generated patch is correct. Local inference, arbitrary login sites, universal secret detection and symlink behavior on this restricted Windows account were not fully verified.

The continuous-task integration test also passed from one prompt: all three portfolio files were created, the CSS/JS references matched them, the HTML was read back and finish_work confirmed completion. It uses a temporary folder, not the user's portfolio. Run it explicitly with scripts/smoke_test.py --live --portfolio. This verifies the tested workflow and artifact references, not browser rendering or JavaScript execution.

If Python says a package is missing, verify that installation and execution use the same .venv interpreter. Re-run pip install with that explicit path. If local configuration fails, inspect variable names, URL and timeout in .env without printing the values. An authentication failure requires checking or replacing the Ollama key through the account locally, not sending it to a chat.

If the model name is unavailable or the API returns an HTTP status, check the account's available cloud models and OLLAMA_MODEL. A rate/credit limit can be handled by waiting for the account allowance or using an installed local model. Connection failures require checking network, VPN, TLS trust or the local server. Do not disable TLS certificate validation as a workaround.

If the response times out after an action, check actual state before retrying. If a webpage is unavailable, try a different primary source or use the returned snippets cautiously; do not label unavailable content as verified. If a code file is blocked, confirm its relative path and that it is a supported small UTF-8 source file; moving secrets into a supported extension is not a solution.

For invalid state, close every running agent and open the active data JSON plus its .json.bak in the editor. Preserve the damaged file under another local name, then copy a valid backup to the active filename and restart. Restore only the affected kind so unrelated tasks/facts remain unchanged. If a stale data/.lock remains after a forced crash, remove it only after confirming no agent instance is running. A normal exit cleans up the lock.

Commands using YES are deliberately case-sensitive. Enter or other answers cancel. Unknown slash commands show /help instead of going to the model. Direct task IDs must be positive integers. A source write rejected because the file changed during approval should be reread and proposed again, preserving the other edit.

## 7. Capabilities, limits and continuing work

The completed first release supports conversation, explicit memory, task management, current web search, public HTML reading, project code inspection, approved small-file changes, in-process history and offline direct commands. Its tested capability matrix is in docs/CAPABILITIES.md. Use it to distinguish implemented behavior from actual test evidence.

Not implemented: arbitrary command execution, automatic test execution, image, audio or PDF ingestion, login/browser automation, scheduled background jobs, reminders, multi-user service, GUI, vector search and unlimited cloud. These are future product choices, not hidden working features. The user selected the terminal version for this release.

PROJECT_STATUS.md records the architecture, scope decision, test results, privacy constraints, report layout and optional future work. When continuing with another collaborator, read it first, then the four original agent-guidelines files. Keep reports bilingual, human-readable and attributed to the project owner. Update test evidence and documentation after each meaningful implementation change rather than claiming a feature from prompt wording alone.

A reasonable next step after using this version is collecting a few real example failures, with secrets removed, and fixing the smallest concrete problem. Larger-file patching or a graphical interface can be planned later. Do not add several frameworks and automation layers before validating the current workflow on your actual daily tasks.

All six contact URLs and the exact author name are defined centrally for the reports. Generated fonts, preview images, PDF files and personal state remain local and ignored by Git. Public source, teaching text and report sources can be reviewed before any manual commit. No commit, push, publication or deployment was performed during this work.
